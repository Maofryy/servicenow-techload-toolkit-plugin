# ACL Fundamentals — how ServiceNow decides who sees what

Reference for the security-review skill. Read it before reasoning about any access question.

---

## 1. Decision types and evaluation order

Every ACL has a `decision_type`. It applies whether or not the ACL has a script.

| decision_type | Meaning | Logic | Evaluated |
|---|---|---|---|
| `deny` — **Deny Unless** | Blocks access unless all its requirements (roles, condition, script) pass | **AND**: every Deny Unless ACL on the object must pass | **First** |
| `allow` — **Allow If** | Grants access if its requirements pass | **OR**: at least one Allow If ACL must pass | **Second** |

Sequence: all Deny Unless pass → then at least one Allow If passes → access granted.
Failing a single Deny Unless ends evaluation: no Allow If is ever checked.

Inside one ACL the requirements combine with AND: roles (any one of the listed roles is enough)
AND condition AND script (`answer`).

## 2. Inheritance and silent fallbacks

- Record-level ACL is checked before field-level ACL. A user needs both `table` read and
  `table.field` read to see a field value.
- If no Allow If ACL exists on `table.operation`, the **parent table's** ACL applies silently
  (e.g. a custom table extending `task` inherits `task` ACLs). An "unprotected" table is often a
  table protected by its parent in ways nobody reviewed.
- Wildcard `table.*` field ACLs cover every field without a specific ACL.
- `admin_overrides = true` lets `admin` bypass the ACL entirely. Normal on record-level ACLs,
  a finding on field-level ACLs protecting sensitive data.
- Inactive (`active = false`) Deny Unless ACL: that gate is silently open.
- Query Business Rules (`sys_script` with `query` trigger) filter rows before ACLs run. They are
  part of row-level security and are invisible in the ACL list.

## 3. Broken and generated ACLs

- `advanced = true` with an empty `script`: broken ACL, behaviour undefined. Treat as a critical
  finding regardless of decision type.
- `security_attribute` non-empty (`SAC_xxxxx`): ACL generated by Security Attribute Control.
  Do not hand-edit; review the attribute instead.
- Several roles on one ACL are OR'ed. Separate ACLs for the same object/operation are OR'ed too
  (Allow If) or AND'ed (Deny Unless).

## 4. Risk signals in ACL scripts

- No `answer = false` default before conditional logic (falls through to `true`).
- `.getValue()` or dotted navigation on a reference field without a nil check (throws → denies
  for everyone, or worse, is wrapped in a try that leaves `answer` true).
- `gs.hasRole('admin')` alone as the whole logic: admin already bypasses; the ACL protects nothing
  for everyone else.
- Checks on `current.sys_created_by` or `opened_by` as the only ownership test: breaks on
  impersonation, integrations and delegated requests.
- Logic duplicated from a Query BR: two places to maintain, they drift.

## 5. Gap detection rules (per table)

Critical
- No active ACL on the table and no meaningful parent ACL.
- `admin_overrides = true` on a field-level ACL guarding sensitive data.
- Broken ACL (`advanced = true`, empty script).
- Inactive Deny Unless ACL.

Warning
- Read ACL exists but write / create / delete missing (operation falls back to parent or to open).
- Field has write protection but no read protection (asymmetric).
- Deny Unless ACLs present but no Allow If on the table: parent fallback in effect.
- Broad roles (`snc_internal`, `itil`, `admin`) used without tighter scoping on sensitive tables.
- Portal or Scripted REST path that bypasses the ACL (server script reading with `GlideRecord`
  instead of `GlideRecordSecure`, or `gs.getUser()` not used).

Info
- SAC-generated ACLs present.
- Script-based ACLs present (translate them in plain language).
- Inactive non-Deny-Unless ACLs present.

## 6. Reading the instance with sn-utils (read-only)

| Question | Table | Useful fields / query |
|---|---|---|
| Which ACLs exist on a table | `sys_security_acl` | `nameSTARTSWITH<table>` → `name, operation, type, decision_type, active, admin_overrides, advanced, condition, script, security_attribute` |
| Which roles each ACL requires | `sys_security_acl_role` | `sys_security_acl.nameSTARTSWITH<table>` → `sys_security_acl, sys_user_role` |
| Role hierarchy (a role containing others) | `sys_user_role_contains` | `role, contains` |
| Who has a role | `sys_user_has_role` | `role.name=<role>` (count with Aggregate API rather than listing) |
| Row filters | `sys_script` | `collection=<table>^when=before^query=true` → `name, condition, script` |
| Client-callable script includes | `sys_script_include` | `client_callable=true^active=true` → `name, access, script` |
| Scripted REST | `sys_ws_definition`, `sys_ws_operation` | `requires_authentication, requires_acl_authorization, script` |
| Portal widgets | `sp_widget` | `name, roles, script, client_script, public` |

An XML export of `sys_security_acl` and `sys_security_acl_role` carries the same fields
(`display_value` attribute for `operation`, `type`, `security_attribute`, `sys_user_role`).
Accept it when provided, but prefer reading the live instance.

## 7. Presenting findings

- Reason in scenarios: "a user with only `snc_internal` opens the portal page X and reads Y".
- Classify by real impact (what data, how many users, how easy), not by count of ACLs.
- Every finding names `table.field` and the operation, and comes with the fix: which ACL to add
  or tighten, which role, which condition, or which script change.
- The roles × operations grid is a useful output when there are many roles; the
  `templates/acl-matrix-template.md` and `acl-gap-report-template.md` files show one shape it can
  take. A colour grid (green Allow If, amber scripted Allow If, red Deny Unless, purple scripted
  Deny Unless, grey no ACL) can be rendered through visual-explainer when it helps the reader.
